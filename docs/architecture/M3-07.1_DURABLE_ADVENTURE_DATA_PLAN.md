## 1. Purpose

M3-07.1 introduces the durable data foundation required for Adventure Companion to support multiple adventures, adventure-specific participants, persistent trip state, memories, pictures, and future scrapbook experiences.

Adventure Companion currently contains durable data in several feature-specific browser storage keys. This milestone consolidates adventure-specific information into a canonical, versioned Adventure Record while preserving existing data and maintaining compatibility with the current Smokies experience.

This milestone is not only a storage refactor.

It establishes the long-term data model required for Adventure Companion to become a living family adventure archive.

---

## 2. Guiding Principle

> **Adventure Companion is a living family adventure archive. Every architectural decision should preserve experiences, support future adventures, and allow memories to be viewed from multiple meaningful perspectives—including adventure, traveler, place, activity, and time—without duplicating the underlying story.**

---

## 3. Milestone Goals

M3-07.1 will establish:

- a versioned canonical Adventure Record;
- a durable global Adventurer Directory;
- adventure-specific participant assignments;
- validation and normalization of stored adventure data;
- safe migration from existing storage keys;
- a dedicated Active Adventure Service;
- durable memory records;
- durable photo storage using IndexedDB;
- adventure-first startup initialization;
- diagnostics for storage, migration, and media;
- export and recovery support;
- regression protection for all existing M3-06 behavior.

---

## 4. Non-Goals

M3-07.1 will not attempt to complete every future scrapbook capability.

The following are outside the initial milestone unless added through a later approved extension:

- advanced printable scrapbook layouts;
- cloud synchronization;
- user accounts;
- multi-device synchronization;
- social sharing;
- real-time collaboration;
- automatic facial recognition;
- automated photo tagging;
- AI-generated scrapbook pages;
- full map-based memory browsing;
- remote media storage;
- destructive removal of all legacy storage before the Smokies trip.

The architecture must support these possibilities without requiring them now.

## 6. Existing Architecture Findings

### 6.1 Existing persistence

Adventure Companion already persists state using multiple feature-specific `localStorage` keys.

Existing persisted concerns include:

- reservations;
- completed days;
- readiness;
- packing;
- welcome and introduction flags;
- feedback;
- campfire state;
- other feature-specific preferences.

M3-07.1 is therefore a consolidation and durability milestone rather than the first introduction of persistence.

### 6.2 Configuration

`config.js` currently exports:

```js
AdventureCompanionConfig;
```

This remains the configuration boundary.

M3-07.1 will not replace the configuration system.

### 6.3 Application build information

`version.js` owns application build metadata, including:

- version;
- milestone;
- cache identifier;
- build information;
- DOM display of build information.

Application build information must remain separate from Adventure Data.

```text
Application Build
└── version.js

Adventure Data
└── Adventure Record
```

Adventure schema versions and application build versions are independent concepts.

### 6.4 Adventure Brain

`adventure-brain.js` already owns context normalization for intelligence processing.

The architecture distinguishes:

```text
Adventure Record normalization
```

from:

```text
Adventure Brain context normalization
```

Adventure Record normalization creates valid durable domain data.

Adventure Brain normalization converts application context into the signal structure required for prioritization and insight generation.

These responsibilities are complementary and must remain separate.

### 6.5 Shared State

The intended integration boundary is:

```text
Durable Storage
        ↓
Active Adventure Service
        ↓
Shared State
        ↓
Adventure Brain
        ↓
Living Campfire
        ↓
Dashboard
```

Shared State should consume the canonical active adventure rather than loading independent durable values from unrelated storage keys.

### 6.6 Current Smokies data

Current Smokies itinerary and trip data are primarily embedded in `app.js`.

During M3-07.1, that information will become canonical seed data for the Smokies Adventure Record.

The existing user experience must remain intact while the ownership of the data changes.

### 6.7 Packing

`packing.js` currently defines travelers and packing state.

The future ownership model is:

```text
Global Adventurer Directory
        ↓
Adventure Participant Assignments
        ↓
Packing
```

Packing must no longer be the permanent authority for who exists in the application.

### 6.8 Service worker

`service-worker.js` handles application asset caching.

It does not own user adventure data.

The service worker may update or replace cached application assets, but normal application updates must not intentionally delete Adventure Records or media stored in IndexedDB.

## 7. Approved Architecture Decisions

### Decision 1 — Adventure-Specific Durable Data

**Status:** Approved  
**Selected option:** Adventure-specific data only

The canonical Adventure Record will contain all durable information belonging to one specific adventure, including:

- participant assignments;
- itinerary;
- reservations;
- packing;
- readiness;
- completion state;
- adventure preferences;
- memories;
- media references;
- future adventure-specific reflections.

The following remain outside the Adventure Record:

- global application preferences;
- the global Adventurer Directory;
- developer feedback;
- build information;
- cache state;
- temporary interface state.

> The canonical Adventure Record will contain all durable information belonging to one specific adventure, including its assigned adventurers, itinerary, reservations, packing, readiness, completion state, preferences, and future memories. Global application preferences, developer feedback, build information, cache state, and temporary interface state will remain outside the Adventure Record.

### Decision 2 — Relational Memories and Media

**Status:** Approved  
**Selected option:** Relational memories with separate media storage

Each memory will be stored once.

A memory may be associated with:

- one adventure;
- one or more adventurers;
- one or more locations;
- one or more itinerary activities;
- a trip date;
- tags;
- one or more media items.

Written memory content and media references will live in the Adventure Record.

Actual picture data will live in a separate durable media store using IndexedDB.

Stable media IDs will connect pictures to memories.

> Each memory will be stored once as a durable record belonging to a specific adventure. A memory may be associated with one or more adventurers, locations, itinerary activities, trip dates, tags, and media items. Written content and media references will live in the canonical Adventure Record, while actual picture files will live in a separate durable media store connected through stable media IDs. The trip-ready release must support written memories, picture attachment, traveler assignment, day, activity, and location relationships, editing, chronological viewing, and durable recovery. This model will later support traveler, location, day, activity, themed, and cross-adventure scrapbooks without duplicating the underlying memory.

### Decision 3 — Global Adventurer Directory

**Status:** Approved  
**Selected option:** Global directory with adventure-specific assignments

Each person will have one stable identity in a global Adventurer Directory.

Each Adventure Record will select its own participants by referencing stable adventurer IDs.

Permanent identity belongs in the global directory.

Adventure-specific state belongs in the Adventure Record.

Global profile example:

```js
{
  id: "jake",
  displayName: "Jake",
  avatar: null,
  relationshipLabel: "Son"
}
```

Adventure assignment example:

```js
{
  adventurerId: "jake",
  role: "traveler",
  includedInReadiness: true,
  adventurePreferences: {}
}
```

Trip-specific packing, readiness, completion, room assignments, roles, and participation must not be stored as permanent global profile attributes.

> Each person will have one stable identity in a durable global Adventurer Directory. Every Adventure Record will select its own participants by referencing those stable adventurer IDs. Packing, readiness, completion, roles, preferences, and other trip-specific state will remain within the relevant Adventure Record or participant assignment rather than the global profile. Memories may reference global adventurer IDs, enabling consistent traveler scrapbooks across multiple adventures without requiring the same people to participate in every adventure.

### Decision 4 — Versioned Staged Migration

**Status:** Approved  
**Selected option:** Safe staged migration with legacy fallback

The application will introduce a canonical versioned Adventure Record while preserving existing legacy storage during the transition.

Migration flow:

```text
Look for canonical Adventure Record
        ↓
Load and validate when found
        ↓
If absent, read legacy storage
        ↓
Convert legacy data
        ↓
Normalize result
        ↓
Save canonical record
        ↓
Retain legacy storage temporarily
```

Legacy storage will remain available as a recovery source through the Smokies trip.

The application must not silently reset invalid or damaged data to an empty adventure.

> Adventure Companion will introduce a versioned canonical Adventure Record as the source of truth for adventure-specific structured data. On first use, the application will safely migrate existing reservation, packing, readiness, completion, and related legacy values into that record. Legacy storage values will remain temporarily available as a recovery source and will not be deleted before the Smokies trip. Future schema changes will use explicit migrations. Actual photo files will be stored separately in IndexedDB and connected through stable media IDs. Loading, validation, normalization, migration, and saving must complete successfully before canonical data is overwritten, and migration failures must be visible through Diagnostics rather than silently resetting user data.

### Decision 5 — Adventure-First Startup

**Status:** Approved  
**Selected option:** Load Adventure Record before Shared State

The canonical Adventure Record must be loaded before Shared State, Adventure Brain, Living Campfire, and Dashboard initialization.

Approved startup flow:

```text
Configuration
        ↓
Build Information
        ↓
Adventure Data Foundation
        ↓
Load Active Adventure
        ↓
Migrate if needed
        ↓
Validate
        ↓
Normalize
        ↓
Shared State
        ↓
Adventure Brain
        ↓
Living Campfire
        ↓
Dashboard
        ↓
Reliability Handshake
```

The Reliability Handshake remains the final startup step.

> During application startup, the canonical Adventure Record will be loaded, migrated when necessary, validated, and normalized before Shared State is initialized. Shared State, Adventure Brain, Living Campfire, and all dashboard components will consume the resulting canonical adventure data rather than loading their own independent state. The Reliability Handshake will remain the final startup step and will verify successful initialization of the complete application stack before the application reports itself as ready.

## 14. Validation

Validation must distinguish between:

- missing data;
- malformed data;
- unsupported schema versions;
- recoverable partial data;
- valid canonical data.

Validation must not silently erase stored information.

Minimum validation should confirm:

- record is an object;
- schema version is supported;
- adventure ID is present;
- required collections are arrays or objects as expected;
- participant assignments contain valid IDs;
- memories contain valid stable IDs;
- media references are arrays;
- date structures are valid enough for normalization.

Validation should return structured results suitable for Diagnostics.

Example:

```js
{
  valid: false,
  errors: [
    {
      path: "participants",
      code: "EXPECTED_ARRAY",
      message: "Participants must be an array."
    }
  ]
}
```

---

## 15. Normalization

Normalization will fill safe defaults without erasing valid user data.

Examples:

- missing memory collection becomes an empty collection;
- missing media reference collection becomes an empty array;
- absent timestamps may become `null`;
- absent optional preferences become defaults;
- unknown readiness values become `"unknown"` rather than false;
- participant collections become normalized arrays;
- legacy reservation structures become canonical reservation items.

Normalization must be deterministic and testable.

## 16. Migration Strategy

The first migration will convert current Smokies storage into schema version 1.

Migration must include available data for:

- reservations;
- completed days;
- packing;
- readiness;
- relevant adventure preferences;
- current Smokies trip metadata.

Migration must preserve existing values whenever possible.

Migration metadata should record:

```js
{
  migratedAt: "...",
  migrationSource: "legacy-local-storage",
  previousSchemaVersion: null
}
```

Migration must be idempotent.

Running startup repeatedly must not create duplicate reservations, participants, packing items, completion records, or memories.

## 17. Active Adventure Service

The Active Adventure Service will become the single application boundary for loading and saving active adventure data.

Proposed responsibilities:

```text
getActiveAdventureId()

createSeedAdventure()
```

Feature modules should not directly own canonical persistence.

## 18. Startup Integration

Startup must follow this sequence:

```text
1. Load configuration.
2. Load build information.
3. Initialize the durable data foundation.
4. Load the global Adventurer Directory.
5. Resolve the active Adventure ID.
6. Load the canonical Adventure Record.
7. Migrate legacy data if canonical data is absent.
8. Validate the Adventure Record.
9. Normalize the Adventure Record.
10. Initialize Shared State.
11. Initialize Adventure Brain.
12. Initialize Living Campfire.
13. Render dashboard and feature views.
14. Run the Reliability Handshake.
```

The application must not report itself ready before the durable data foundation has succeeded.

> **"Our family's adventure book that somehow knows exactly what we need today."**

Every architectural decision should make that vision easier to achieve.

## 26. Acceptance Criteria

M3-07.1 is complete when:

- a canonical schema-versioned Smokies Adventure Record exists;
- the active adventure loads before Shared State;
- existing Smokies data migrates without intentional loss;
- legacy storage remains available as a temporary fallback;
- the global Adventurer Directory contains stable identities;
- each adventure selects its own participants;
- readiness and packing remain adventure-specific;
- memories support traveler, location, activity, and date relationships;
- photos are stored outside the Adventure Record using IndexedDB;
- normal application updates do not intentionally erase Adventure Data;
- Diagnostics reports Adventure Data health;
- structured Adventure Data can be exported;
- the existing M3-06 user experience remains functional;
- the complete automated test suite passes;
- the repository is clean after the final release commit.
