# M3-06.1 Adventure Brain Architecture

- **Project:** Adventure Companion
- **Milestone:** M3-06.1 – Adventure Brain Foundation
- **Status:** Implemented
  **Build:** M3-06.1 Foundation

---

# Purpose

Adventure Brain is the application's central decision engine.

Its responsibility is to evaluate the current adventure context and determine what deserves the user's attention without making any decisions about how information is displayed.

Adventure Brain intentionally separates intelligence from presentation.

The module evaluates signals, ranks priorities, and produces a single structured result that the user interface can render in any way it chooses.

---

# Design Goals

The Adventure Brain was designed around several core principles.

## Calm before clever

The application should never overwhelm the user.

Even when multiple events are occurring simultaneously, the Adventure Brain identifies the single most important Daily Focus while preserving additional insights for future use.

---

## One source of intelligence

Only one module should decide what matters today.

This prevents competing logic from appearing across multiple UI components.

---

## Presentation independent

Adventure Brain never:

- modifies the DOM
- renders HTML
- updates CSS
- displays notifications
- manipulates components

Instead it returns structured information describing what the application should display.

---

## Graceful degradation

Missing information should never break the application.

Every signal must resolve into one of three known states.

```
AVAILABLE
UNAVAILABLE
UNKNOWN
```

This guarantees deterministic behavior even when data sources are unavailable.

# Responsibilities

Adventure Brain is responsible for:

- interpreting application context
- normalizing incoming data
- evaluating signals
- ranking priorities
- selecting one Daily Focus
- exposing supporting insight

Adventure Brain is intentionally **not** responsible for:

- rendering
- styling
- navigation
- persistence
- weather retrieval
- packing calculations
- itinerary generation

---

# Signal Model

Each signal represents one piece of information that may influence the user's attention.

Every signal follows the same structure.

```
Signal
 ├── id
 ├── category
 ├── state
 ├── active
 ├── priorityTier
 └── evidence
```

Signals are immutable after creation.

---

# Signal States

Every signal exists in exactly one state.

| State       | Meaning                              |
| ----------- | ------------------------------------ |
| AVAILABLE   | Required information exists          |
| UNAVAILABLE | Information is known but unavailable |
| UNKNOWN     | Information cannot yet be determined |

Unknown is intentionally different from unavailable.

This distinction allows the application to communicate uncertainty without implying failure.

---

# Priority Model

Adventure Brain evaluates many possible signals while exposing only the most important Daily Focus.

Priority order is intentionally fixed.

| Tier | Purpose                                        |
| ---- | ---------------------------------------------- |
| 1    | Safety and severe weather                      |
| 2    | Confirmed reservations and travel requirements |
| 3    | Adventure discovery and encouragement          |
| 4    | Memory and reflection                          |
| 5    | Preparation risk                               |
| 6    | Tomorrow readiness                             |
| 7    | Individual readiness                           |
| 8    | Family readiness                               |

This ordering represents product decisions rather than implementation details.

---

# Context Normalization

Incoming application data may originate from multiple independent systems.

Before evaluation, Adventure Brain converts all input into a predictable structure.

Normalization allows future modules to evolve independently without affecting evaluation logic.

---

# Evaluation Pipeline

Adventure Brain processes information using a simple pipeline.

```
Raw Context
      │
Normalize Context
      │
Create Signals
      │
Evaluate Signals
      │
Create Focus Candidates
      │
Rank Candidates
      │
Select Daily Focus
      │
Return Structured Result
```

Every stage has a single responsibility.

---

# Browser Integration

The browser loads Adventure Brain before the main application.

```
index.html
      │
adventure-brain.js
      │
app.js
      │
AdventureReliability
```

This guarantees that the application can safely determine whether Adventure Brain is available before evaluation begins.

---

# Reliability Philosophy

Adventure Brain must never prevent the application from starting.

Evaluation always occurs inside a protected execution block.

Unexpected failures result in:

- safe fallback
- null state
- application continues normally

Reliability is considered more important than intelligence.

---

Caching ensures:

# Architectural Principles

Future development should preserve the following principles.

- Intelligence before presentation.
- One Daily Focus.
- Deterministic priority ordering.
- Presentation independence.
- Graceful degradation.
- Immutable evaluation results.
- Small, testable functions.
- Backwards compatibility whenever possible.

---

# Summary

Adventure Brain establishes the intelligence foundation for Adventure Companion.

Rather than allowing every feature to independently determine what deserves attention, the application now has a single decision engine responsible for interpreting adventure context.

This architecture keeps the user experience calm, predictable, extensible, and easy to maintain while providing a foundation for future intelligent behavior throughout the application.
