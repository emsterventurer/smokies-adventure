# M3-06.3 Living Campfire Plan

## Status

**Milestone:** M3-06.3 Living Campfire  
**Project:** Adventure Companion  
**Status:** Design complete — ready for implementation planning  
**Depends on:**

- M3-06.1 Adventure Brain Foundation
- M3-06.2 Dynamic Dashboard

---

## 1. Purpose

Living Campfire gives Adventure Companion its warm, contextual Remy experience.

Adventure Brain determines what deserves attention.

The Dynamic Dashboard presents operational information.

Living Campfire interprets a dedicated communication contract from Adventure Brain and returns one calm, meaningful Campfire experience in Remy's voice.

Living Campfire answers:

> How should Remy respond to today's adventure context?

It does not replace Adventure Brain.

It does not replace the Dynamic Dashboard.

It does not create a second intelligence system.

Instead, it turns Adventure Brain's conclusions into a grounded, recognizable, emotionally supportive experience.

---

## 2. Experience Philosophy

Living Campfire should feel like a steady companion rather than a random message generator.

The experience follows six principles.

### 2.1 Warm and recognizable

Remy should have a consistent, encouraging voice that feels personal without becoming overly theatrical.

The user should recognize the tone as Remy even when the category, phase, or topic changes.

### 2.2 Grounded in real context

Living Campfire must not invent:

- weather
- reservations
- accomplishments
- emotions
- memories
- itinerary details
- packing status
- readiness milestones
- family activity
- travel conditions

Every contextual statement must be supported by the structured `remyContext` produced by Adventure Brain.

### 2.3 Calm rather than chatty

Living Campfire presents one primary message.

It may also provide one optional supporting prompt.

It must not display several competing stories, reflections, celebrations, reminders, or encouragement messages simultaneously.

The experience should help the user know where to place attention without creating more decision fatigue.

### 2.4 Phase-aware

The tone and purpose of the message may change across the adventure lifecycle:

- planning
- countdown
- departure or travel
- active trip
- return
- reflection

Phase awareness may influence tone, category, and wording.

Phase awareness must not create unsupported specificity.

### 2.5 Helpful without duplicating the Dashboard

The Dashboard remains the source of operational truth.

Living Campfire may refer the user toward Dashboard information, but it should not restate detailed facts such as:

- exact departure times
- reservation details
- forecasts
- packing counts
- diagnostic information
- raw readiness percentages
- full itinerary details

### 2.6 Graceful with limited context

Missing or unavailable data must not create fabricated specificity or visible errors.

When meaningful context is limited, Living Campfire should provide a safe, light-touch message.

A fallback message should feel intentional rather than broken.

## 3. Core Architectural Principles

### 3.1 Living Campfire interprets Adventure Brain

> Living Campfire interprets Adventure Brain. It does not compete with it.

Adventure Brain decides what deserves attention.

Living Campfire decides how Remy should respond to that decision.

Living Campfire must not establish a separate priority-ranking system.

### 3.2 One Daily Conversation

Adventure Brain provides one Daily Focus.

Living Campfire provides one primary Campfire conversation.

An optional supporting prompt may accompany that message when it adds meaningful value.

### 3.3 Dashboard authority

> The Dashboard is the source of operational truth. Living Campfire provides the emotional and narrative layer around that truth.

Living Campfire should acknowledge important operational context without replacing or duplicating it.

### 3.4 Context stability

> The same meaningful context should produce the same Campfire experience.

A browser refresh, application restart, or repeated visit must not cause unnecessary message changes.

Messages should change only when meaningful context changes.

### 3.5 Presentation independence

Living Campfire returns structured data.

It does not generate HTML.

It does not manipulate the DOM.

It does not own layout, styling, animation, or rendering.

### 3.6 Graceful extension

Adventure Brain may extend `remyContext` in future milestones.

Living Campfire should ignore unknown optional fields safely and continue producing a valid experience.

## 4. Responsibilities

### 4.1 Living Campfire is responsible for

- interpreting `remyContext`
- selecting an appropriate message category
- selecting grounded message content
- applying Remy's consistent voice
- producing one primary message
- optionally producing one supporting prompt
- remaining stable for equivalent context
- providing safe fallback content
- exposing structured output for presentation
- preserving the separation between operational truth and narrative response
- rejecting unsupported specificity through safe fallback behavior

### 4.2 Living Campfire is not responsible for

- ranking priorities
- choosing the Daily Focus
- calculating weather
- evaluating packing readiness
- evaluating reservation urgency
- calculating departure suggestions
- reading raw itinerary data independently
- reading raw reservation data independently
- reading raw weather data independently
- reading raw packing data independently
- reading family-readiness data independently
- manipulating the DOM
- rendering interface components
- fetching data
- storing application state
- producing random messages on refresh
- overriding Adventure Brain conclusions
- reconstructing information omitted from `remyContext`

## 5. System Boundaries

The intended relationship is:

```text
Structured Trip Data
        │
        ▼
Adventure Brain
"What deserves attention?"
        │
        ├────────────────────► Dynamic Dashboard
        │                      Shows operational truth
        │
        ▼
remyContext
Compact communication contract
        │
        ▼
Living Campfire
"How should Remy respond?"
        │
        ▼
Structured Campfire Experience
        │
        ▼
Remy's Campfire UI
```

### 5.1 Boundary summary

Adventure Brain owns analysis and interpretation.

`remyContext` carries only the communication context needed by Living Campfire.

Living Campfire owns message selection, tone, and structured narrative output.

The browser layer owns presentation.

### 5.2 Boundary rules

Living Campfire must not bypass `remyContext`.

The browser must not ask Living Campfire to analyze raw application data.

The Dashboard and Living Campfire may respond to the same Adventure Brain evaluation, but each remains responsible for a different presentation purpose.

## 6. Campfire Experience Model

Living Campfire returns one structured Campfire experience.

That experience contains:

- one primary message
- one optional supporting prompt
- presentation-independent metadata

The model must remain small, stable, and testable outside the browser.

Conceptually:

```javascript
{
  message: {
    category: "encouragement",
    title: "A calm start",
    body: "Today only needs one good next step."
  },

  prompt: {
    label: "What would make today feel easier?",
    type: "reflection"
  },

  meta: {
    contextKey: "countdown|departure|2026-08-07",
    state: "available"
  }
}
```

The exact wording may evolve during implementation.

The output shape may be extended only when the addition supports a clear presentation or testing need without exposing raw application data.

## 7. Message Categories

Living Campfire may produce a primary message from a small set of approved categories.

Initial categories are:

- `encouragement`
- `reflection`
- `celebration`
- `discovery`
- `light-touch`

### 7.1 Encouragement

Used when Adventure Brain identifies:

- a meaningful next step
- a preparation need
- a stress-risk moment
- a transition that benefits from reassurance
- a situation where calm perspective adds value

Encouragement should support action without sounding urgent unless Adventure Brain has already identified meaningful urgency.

### 7.2 Reflection

Used when the current phase or milestone supports:

- looking back
- noticing progress
- acknowledging meaning
- inviting a brief personal observation
- preparing for post-trip storytelling

Reflection must remain grounded in known milestones or phase information.

### 7.3 Celebration

Used when Adventure Brain identifies a grounded achievement or readiness milestone.

Examples may include:

- an individual becoming ready
- the family becoming ready
- a meaningful preparation milestone
- a completed adventure milestone

Celebrations must be based on structured application state and must not be invented.

### 7.4 Discovery

Used when there is room to invite:

- curiosity
- anticipation
- gentle exploration
- attention to a meaningful detail
- openness to an unplanned moment

Discovery should not introduce operational urgency.

### 7.5 Light-touch

Used when contextual information is:

- unavailable
- incomplete
- unsupported
- unknown
- not meaningful enough to justify a more specific response

Light-touch messages must remain warm while avoiding fabricated specificity.

### 7.6 Category constraints

Only one primary category may be selected for a Campfire experience.

The optional prompt may support the selected category but must not introduce a competing message category.

Category selection must remain deterministic for equivalent context.

## 8. Relationship to Daily Focus

Living Campfire responds to Adventure Brain's interpretation of the current Daily Focus.

It must not select, replace, or reprioritize the Daily Focus.

The relationship is:

```text
Adventure Brain
        │
        ▼
Daily Focus
        │
        ▼
remyContext
        │
        ▼
Living Campfire response
```

The Dashboard presents the operational meaning of the Daily Focus.

Living Campfire provides the emotional, narrative, encouraging, celebratory, or reflective response around it.

For example:

- The Dashboard may show that a confirmed departure suggestion deserves attention.
- Living Campfire may encourage the family to create a calm start.
- Living Campfire must not restate the departure time or reservation details.

When no meaningful Daily Focus is available, Adventure Brain may provide a light-touch `remyContext`.

### 8.1 Daily Focus restrictions

Living Campfire must not:

- create a new Daily Focus
- alter the Daily Focus identifier
- compare several candidate priorities
- infer operational details from the Daily Focus identifier
- restate information not explicitly carried in `remyContext`

## 9. Context Stability

Living Campfire should provide a consistent experience for equivalent context.

Equivalent input should produce equivalent output.

The Campfire experience should change only when meaningful context changes, such as:

- the current day changes
- the trip phase changes
- the Daily Focus changes
- a meaningful milestone is reached
- Adventure Brain produces a different `remyContext`
- a supported message-mode input changes
- a stable context identifier changes

The Campfire experience should not change because:

- the browser refreshes
- the application restarts
- the user revisits the page
- unrelated application state changes
- time passes without a meaningful context change
- message generation is random

### 9.1 Context identifier

Living Campfire should include a stable context identifier within its output metadata.

Conceptually:

```javascript
meta: {
  contextKey: "countdown|focus-departure|2026-08-07",
  state: "available"
}
```

The exact composition may evolve, but the key must be derived from normalized communication context rather than browser state.

### 9.2 Deterministic selection

When more than one message is valid for the same category, Living Campfire must use deterministic selection.

Possible implementation approaches include:

- mapping one context key to one catalog entry
- using a stable hash
- selecting by normalized topic and phase
- using a fixed precedence order

Random selection is not permitted in M3-06.3.

### 9.3 Stability guarantee

Equivalent normalized input should produce:

- the same category
- the same primary message
- the same prompt presence or absence
- the same metadata context key
- the same metadata state

## 10. Remy's Voice

Living Campfire must use a consistent Remy voice.

The voice should be:

- warm
- calm
- encouraging
- observant
- concise
- grounded
- gently adventurous

The voice should not be:

- overly dramatic
- overly sentimental
- childish
- preachy
- repetitive
- vague when useful context exists
- falsely specific when context is limited
- demanding
- guilt-based
- alarmist unless Adventure Brain has identified a safety concern

### 10.1 Voice behavior

Remy should acknowledge the current context without overwhelming the user.

Messages should generally:

- use plain language
- focus on one idea
- use concise sentences
- avoid excessive exclamation points
- avoid repeating Dashboard details
- avoid implying emotions the user has not expressed
- avoid claiming memories or achievements not supported by data
- use adventure language lightly rather than constantly
- leave room for the user's own interpretation
- support one calm next step when appropriate

### 10.2 Appropriate examples

> One calm step is enough for today.

> The adventure is getting closer. You do not have to prepare for all of it at once.

> That is one more piece ready for the road.

> Today has room for one good discovery.

> The plan is there. Now the family can move through it calmly.

### 10.3 Less appropriate examples

> Everything is absolutely perfect and the whole family is bursting with excitement!

> You must finish packing immediately.

> This will be the best trip of your life.

> You are obviously stressed, so calm down.

> I remember how much everyone loved this last time.

### 10.4 Grounding rule

Living Campfire may communicate only what `remyContext` supports.

When wording would require unsupported details, it must choose a more general message or return the light-touch fallback.

## 11. Input Contract

Living Campfire receives a dedicated `remyContext` object produced by Adventure Brain.

It does not receive the complete Adventure Brain state.

It must not independently read raw browser data.

Conceptually:

```javascript
const adventureBrainState = AdventureBrain.evaluate(rawContext);

const campfireExperience = LivingCampfire.evaluate(
  adventureBrainState.remyContext,
);
```

### 11.1 Ownership

Adventure Brain owns the `remyContext` contract.

Adventure Brain is responsible for converting operational and readiness signals into a compact communication context suitable for Living Campfire.

Living Campfire is responsible for expressing that context through Remy's voice.

### 11.2 Initial contract

The current Adventure Brain fallback shape establishes this initial contract:

```javascript
{
  mode: "light-touch",
  primaryTopic: null,
  dailyFocusId: null,
  avoidTopics: [],
  state: "unknown"
}
```

The contract may evolve during M3-06.3 as required, but additions must remain:

- presentation-independent
- normalized
- grounded in Adventure Brain conclusions
- safe when incomplete
- backward-compatible where practical
- free of raw browser or DOM state

### 11.3 Potential contract evolution

Potential future fields may include:

```javascript
{
  mode: "encouragement",
  primaryTopic: "departure",
  dailyFocusId: "departure-focus",
  avoidTopics: ["weather"],

  milestone: {
    type: "individual-ready",
    subjectId: "emily"
  },

  contextDate: "2026-08-01",
  phase: "countdown",
  state: "available"
}
```

These fields are illustrative.

Each field must be approved before implementation.

### 11.4 Field expectations

#### `mode`

Communicates the intended response mode.

Initial supported values may include:

- `encouragement`
- `reflection`
- `celebration`
- `discovery`
- `light-touch`

Unsupported values must fall back safely.

#### `primaryTopic`

Provides a normalized topic selected by Adventure Brain.

Living Campfire may use it for message selection but must not infer raw operational details from it.

#### `dailyFocusId`

Provides a stable reference to the Adventure Brain focus that informed the communication context.

It is not intended for display.

#### `avoidTopics`

Provides topics Living Campfire should avoid mentioning.

It must be treated as a constraint, not as a source of new message content.

#### `state`

Communicates the availability of the contract.

Initial expected values may include:

- `available`
- `unavailable`
- `unknown`

Unsupported states must fall back safely.

#### Optional milestone metadata

May describe a grounded event or readiness milestone.

Living Campfire must not invent milestone meaning beyond the supplied normalized values.

#### Optional phase and date metadata

May support deterministic and phase-aware selection.

They must be normalized before reaching Living Campfire.

### 11.5 Living Campfire restrictions

Living Campfire must not independently inspect:

- `DAY_DASH`
- itinerary records
- reservation records
- weather data
- packing data
- family-readiness data
- raw Adventure Brain signals
- DOM state
- browser storage
- global UI variables

It must not reconstruct or override Adventure Brain decisions.

### 11.6 Required input behavior

Living Campfire must safely handle:

- no argument
- `null`
- an empty object
- missing properties
- an unknown `state`
- an unavailable `state`
- an unsupported `mode`
- a missing `primaryTopic`
- an empty `avoidTopics` collection
- a malformed `avoidTopics` value
- malformed optional metadata
- unknown future optional properties

Incomplete or unsupported input must produce a valid light-touch fallback experience rather than a normal-use exception.

### 11.7 Normalization boundary

Adventure Brain should provide normalized `remyContext`.

Living Campfire may perform defensive normalization only to protect itself from malformed input.

Defensive normalization must not become a second interpretation engine.

## 12. Output Contract

Living Campfire returns one structured Campfire experience.

The output must remain presentation-independent so it can be tested without the browser interface.

Conceptually:

```javascript
{
  message: {
    category: "encouragement",
    title: "A calm start",
    body: "Today only needs one good next step."
  },

  prompt: {
    label: "What would make today feel easier?",
    type: "reflection"
  },

  meta: {
    contextKey: "countdown|departure|2026-08-07",
    state: "available"
  }
}
```

### 12.1 Required properties

The output must always include:

- `message`
- `meta`

The `prompt` property must be present and may be `null`.

### 12.2 Message object

The `message` object must include:

- `category`
- `title`
- `body`

The category must be one of the approved message categories.

The title and body must be safe for direct presentation in the interface.

They must not contain:

- HTML
- placeholder tokens
- undefined values
- raw diagnostic text
- unsupported operational detail

### 12.3 Prompt object

When present, the `prompt` object may include:

- `label`
- `type`

The prompt must support the primary message rather than introduce a competing topic.

The prompt must not be required for the primary message to make sense.

A prompt should be omitted when:

- context is too limited
- it would add decision fatigue
- it would duplicate the Dashboard
- it would imply unsupported emotion
- it would introduce a second priority

### 12.4 Metadata object

The `meta` object must include:

- `contextKey`
- `state`

The metadata may later include approved diagnostic or selection information, such as:

- selected catalog identifier
- normalized mode
- normalized topic
- fallback reason code

Any additional metadata must remain presentation-independent.

Metadata must not contain:

- HTML
- DOM references
- raw reservation records
- raw weather records
- raw packing records
- raw itinerary records
- full Adventure Brain state

### 12.5 Output guarantees

Living Campfire must always return:

- a valid object
- one valid primary message
- a valid metadata object
- either one supporting prompt or `null`
- no HTML
- no DOM references
- no raw application records

Unsupported or incomplete input must still produce a valid light-touch experience.

### 12.6 Immutability expectation

The browser rendering layer should treat the returned object as read-only.

Rendering must not modify the experience object.

Tests may freeze representative objects to confirm presentation independence where useful.

### 12.7 Example light-touch output

```javascript
{
  message: {
    category: "light-touch",
    title: "One step at a time",
    body: "Every adventure begins with a single next step."
  },

  prompt: null,

  meta: {
    contextKey: "fallback",
    state: "unavailable"
  }
}
```

## 13. Failure Behavior

Living Campfire must fail gracefully.

The user experience should remain calm and functional even when Adventure Brain cannot provide complete context.

### 13.1 Never fail visibly

Living Campfire should never expose:

- JavaScript exceptions
- stack traces
- placeholder variables
- undefined values
- incomplete templates
- raw diagnostic messages
- serialized application objects

Unexpected conditions must produce a safe fallback experience.

### 13.2 Safe fallback behavior

When `remyContext` is unavailable, unsupported, or incomplete, Living Campfire should return a valid light-touch experience.

The fallback experience should feel intentional rather than like an error condition.

### 13.3 Unknown future data

Living Campfire should ignore unsupported optional properties rather than failing.

Future versions of Adventure Brain should be able to extend `remyContext` without breaking older Campfire implementations.

### 13.4 Unsupported modes

An unsupported `mode` must not produce a partial message.

It should route to light-touch behavior and use metadata that indicates fallback occurred.

### 13.5 Malformed collections

Malformed values such as a non-array `avoidTopics` field must be normalized defensively or ignored.

They must not trigger a visible exception.

### 13.6 Rendering-layer failure

If the browser cannot render an optional prompt, the primary message should remain usable.

The primary Campfire message must not depend on optional presentation behavior.

### 13.7 Diagnostic observability

Normal users should see a calm fallback.

Developer diagnostics may record a concise non-sensitive reason code outside Living Campfire's user-facing content.

Diagnostic support must not leak into the displayed message.

## 14. Testing Strategy

Living Campfire should be tested independently of the browser interface.

The primary testing target is the structured output contract.

### 14.1 Unit tests

Tests should verify:

- valid output for valid input
- valid fallback for missing input
- valid fallback for `null`
- valid fallback for an empty object
- stable output for equivalent context
- different output when meaningful context changes
- supported message categories
- required metadata
- safe handling of unknown modes
- safe handling of malformed input
- safe handling of unknown future fields
- prompt presence or absence
- no HTML in output
- no raw application records in output
- avoidance constraints are respected
- one primary category is selected

### 14.2 Determinism tests

Tests should verify that repeated evaluation of equivalent normalized context returns equivalent output.

Tests should also verify that:

- refresh-like repetition does not change selection
- unrelated omitted data does not affect output
- a changed context key may change output
- random APIs are not used for message selection

### 14.3 Contract tests

Tests should verify the required input and output shapes.

Representative tests should cover:

- minimum valid `remyContext`
- full supported `remyContext`
- malformed optional metadata
- unsupported mode
- unavailable state
- unknown state
- valid celebration milestone
- valid discovery context
- light-touch fallback

### 14.4 Integration tests

Integration tests should verify:

- Adventure Brain provides a valid `remyContext`
- Living Campfire consumes only `remyContext`
- Dashboard and Campfire remain independent
- browser rendering uses structured output without modifying it
- existing Dashboard behavior remains healthy
- Adventure Brain fallback state remains safe
- missing Campfire context does not break page rendering

### 14.5 Voice and content tests

Tests may verify approved content characteristics through catalog assertions rather than brittle sentence-by-sentence prose matching.

Examples:

- every catalog entry has a supported category
- every entry has a title and body
- no entry contains forbidden placeholders
- no entry contains HTML
- celebration entries require milestone context
- operational details are not embedded in generic messages

### 14.6 Non-goals

Tests should not depend on:

- CSS
- browser timing
- animations
- random selection
- network requests
- visual pixel matching
- exact punctuation for every message
- full DOM snapshots unless required by existing project conventions

### 14.7 Manual review

Before completion, manually review:

- Remy's tone
- message clarity
- absence of duplicated Dashboard details
- fallback quality
- prompt usefulness
- stability across refreshes
- behavior across supported trip phases
- reduced-motion compatibility in the browser layer

## 17. Approved Design Decisions

The following architectural decisions have been approved.

### Decision 1 — One Daily Conversation

Adventure Brain provides one Daily Focus.

Living Campfire provides one primary Campfire conversation with one optional supporting prompt.

### Decision 2 — Dashboard Authority

The Dashboard remains the source of operational truth.

Living Campfire provides the emotional, narrative, and reflective layer around that truth.

### Decision 3 — Stable Context

Equivalent context should produce equivalent Campfire experiences.

Messages should not change because of refreshes or application restarts.

### Decision 4 — Dedicated Communication Contract

Living Campfire consumes only the `remyContext` contract produced by Adventure Brain.

It must not inspect raw application data or the complete Adventure Brain state.

### Decision 5 — Presentation Independence

Living Campfire returns structured data only.

It does not manipulate the DOM or generate HTML.

Rendering belongs to the browser layer.

### Decision 6 — Graceful Fallback

Incomplete, unavailable, or unsupported context produces a valid light-touch experience.

It does not create visible errors.

### Decision 7 — No Random Refresh Behavior

Message selection must be deterministic for equivalent context.

Random selection is outside the scope of M3-06.3.

### Decision 8 — Grounded Celebrations

Celebration messages require a supported milestone from Adventure Brain.

Living Campfire must not infer or invent achievements.

### Decision 9 — One Primary Category

Each Campfire experience has one primary message category.

An optional prompt may support that category but must not introduce a competing topic.

## Summary

Adventure Brain determines what deserves attention.

The Dynamic Dashboard presents operational truth.

`remyContext` provides a compact communication contract.

Living Campfire transforms that contract into one calm, grounded conversation in Remy's voice.

Together these systems create an experience that is:

- intelligent without being intrusive
- warm without being artificial
- stable without becoming repetitive
- helpful without competing for attention
- grounded without becoming mechanical
- extensible without blurring responsibilities

This document serves as the official architectural blueprint for M3-06.3 Living Campfire.
