# M3-07.2 Adventure Memories & Timeline

**Status:** Planning
**Milestone:** M3-07.2
**Depends On:** M3-07.1 Durable Adventure Data
**Target Experience:** Smokies Adventure, August 7–14, 2026

---

## 1. Vision

Adventure Memories & Timeline transforms Adventure Companion from a trip-planning application into a living family journal.

The release should make it easy to capture meaningful moments while an adventure is happening, organize those moments into a coherent family story, and revisit them later through a polished chronological Adventure Book.

Every memory should be:

- Quick to capture during the adventure.
- Easy to enrich later.
- Connected to the people, places, activities, and dates that gave it meaning.
- Pleasant to browse on both mobile and desktop.
- Durable enough to support future statistics, exports, sharing, and cloud collaboration.

The experience should feel calm, personal, and intentional rather than like a generic photo-management system.

---

## 2. Product Philosophy

Adventure Companion is evolving toward four connected roles:

1. **Planner before the adventure**
2. **Guide during the adventure**
3. **Journal after each day**
4. **Scrapbook for years afterward**

M3-07.2 establishes the journal and scrapbook foundation.

The release should support quick individual capture during the day while also encouraging a shared evening ritual around the family campfire.

The application should preserve one coherent Adventure Book while still allowing each memory to identify which adventurers contributed, participated, or were featured.

---

## 3. Primary Goals

M3-07.2 will:

- Create a chronological Adventure Book.
- Provide complete memory creation and editing.
- Improve photo attachment and photo presentation.
- Support favorite memories.
- Support reusable tags.
- Link memories to activities and reservations.
- Add timeline navigation.
- Add memory search.
- Add memory filtering.
- Add an immersive photo viewer.
- Preserve compatibility with the M3-07.1 Adventure Record.
- Prepare the data foundation for M3-07.3 Adventure Statistics.
- Prepare the presentation foundation for M3-07.4 Export & Sharing.

---

## 4. Non-Goals

M3-07.2 will not implement:

- User accounts.
- Cloud synchronization.
- Cross-device data sharing.
- Real-time collaboration.
- Public Adventure links.
- Contributor invitation links.
- QR-code submissions.
- Multi-user conflict resolution.
- Multiple Adventure management.
- Automated AI-written stories.
- PDF export.
- Printable scrapbook generation.
- Advanced trip statistics.

These capabilities belong to later milestones.

Contributor Mode remains a future feature that will depend on Adventure Cloud or another shared-data transport layer.

---

## 5. Success Criteria

At the completion of M3-07.2, Emily should be able to:

- Capture a basic memory in under one minute.
- Add a title, story, date, time, and location.
- Associate one or more adventurers with the memory.
- Link the memory to an activity or reservation.
- Attach multiple photos.
- Reorder attached photos.
- Select a cover photo.
- Edit a saved memory.
- Delete a memory intentionally.
- Mark or unmark a favorite.
- Add and remove tags.
- Browse memories chronologically.
- Jump directly to a specific Adventure day.
- Search memory titles, stories, locations, and tags.
- Filter by day, adventurer, favorite status, tag, or linked activity.
- Open photos in a larger viewer.
- Move between photos without closing the viewer.
- Use the experience comfortably on a phone.
- Reload the application without losing memories or media.

## 7. User Experience Principles

### 7.1 Capture First

Memory capture should prioritize speed.

The first visible fields should be limited to the information most likely to be entered during the adventure:

- Title
- Date
- Story or note
- Photos

Additional metadata should remain available without making quick capture feel heavy.

### 7.2 Enrich Later

A memory may begin as a short sentence and one photo.

Emily should be able to return later and add:

- More detail
- Adventurers
- Location
- Tags
- Activity links
- Favorite status
- Cover-photo selection

### 7.3 Mobile First

The primary capture device for the Smokies trip will likely be a phone.

Controls must therefore:

- Work well with touch.
- Avoid tiny targets.
- Avoid horizontally crowded layouts.
- Keep primary actions within easy reach.
- Support narrow screens without losing functionality.
- Avoid requiring hover.

### 7.4 One Family Story

Memories may include individual perspectives, but the Adventure Book should remain one coherent family record.

A memory can identify:

- Who participated.
- Who contributed the story.
- Who appears in attached media.
- Which family member supplied a quote or favorite moment.

Full remote contribution is not included in this release.

### 7.5 Calm Visual Design

The Adventure Book should feel reflective and inviting.

It should not resemble:

- A spreadsheet.
- A social-media feed.
- A file manager.
- A generic administrative form.

The visual language should continue the established Adventure Companion style:

- Smoky green
- Warm campfire accents
- Mountain and trail imagery
- Spacious cards
- Clear typography
- Gentle motion
- Accessible contrast

## 8. Memory Data Model

The existing memory structure will be extended through normalization and migration rather than replaced abruptly.

Each memory should support the following conceptual structure:

```js
{
  id: "memory-stable-id",
  adventureId: "smokies-2026",

  title: "Our First Smokies Dinner",
  story: "Everyone finally arrived and we celebrated at Local Goat.",

  occurredAt: "2026-08-07T18:00:00-04:00",
  date: "2026-08-07",
  time: "18:00",
  timezone: "America/New_York",

  location: {
    name: "Local Goat",
    address: "",
    latitude: null,
    longitude: null
  },

  participantIds: [
    "emily",
    "jake",
    "kaseryn",
    "bubbe",
    "papa"
  ],

  contributorIds: [
    "emily"
  ],

  activityIds: [],
  reservationIds: [],

  tags: [
    "arrival-day",
    "family-dinner"
  ],

  updatedAt: "2026-08-07T22:15:00-04:00"
```

The exact implementation may retain existing property names when doing so avoids unnecessary migration risk.

The architecture must favor backward compatibility over cosmetic renaming.

## 9. Required Memory Fields

A valid memory must contain:

- Stable memory ID.
- Adventure ID.
- Title or generated fallback title.
- Valid Adventure date or timestamp.
- Created timestamp.
- Updated timestamp.

The memory may safely default:

- Story to an empty string.
- Participant IDs to an empty array.
- Contributor IDs to the current organizer when appropriate.
- Activity IDs to an empty array.
- Reservation IDs to an empty array.
- Tags to an empty array.
- Favorite to `false`.
- Media IDs to an empty array.
- Cover media ID to `null`.
- Location to an empty normalized object.

---

## 10. Memory Identity Rules

Memory IDs must:

- Remain stable after editing.
- Never be replaced by form input.
- Never depend on the title.
- Never depend on array position.
- Remain unique within an Adventure.
- Be safe for media relationships.
- Be safe for future exports and cloud synchronization.

Editing a memory must not create a replacement identity unless the user explicitly duplicates it in a future feature.

---

## 11. Chronology Rules

The Adventure Book will use the following ordering rules:

1. Primary order: memory occurrence date and time.
2. Secondary order: created timestamp.
3. Final deterministic order: stable memory ID.

Memories should display oldest-to-newest inside the chronological Adventure Book unless the user selects a reversed view.

Quick Memory Capture may continue to show recently created memories newest-first where that interaction is more useful.

Memories without a specific time should still appear on the correct day.

Memories created after the trip but assigned to a trip date should appear on the assigned Adventure day.

## 16. Photo Attachment Workflow

The photo workflow should support:

- Selecting one or multiple local image files.
- Saving media bytes to IndexedDB.
- Saving media metadata with stable media IDs.
- Associating media records with an Adventure and memory.
- Displaying an upload or processing state.
- Handling unsupported or unreadable files gracefully.
- Removing a photo without deleting the whole memory.
- Preserving the remaining gallery order.

The memory record should reference media IDs rather than embedding photo data directly.

## 18. Photo Layouts

Memory galleries should adapt to the number of photos.

Suggested layouts:

- One photo: large hero image
- Two photos: balanced split
- Three photos: one large plus two smaller
- Four photos: two-by-two grid
- More than four: featured cover plus compact grid and photo-count overlay

The layout must:

- Preserve useful cropping.
- Avoid extreme stretching.
- Work on narrow screens.
- Retain clear touch targets.
- Avoid loading every full-resolution image into view unnecessarily.

Initial implementation may prioritize correctness and responsiveness before advanced masonry layouts.

---

## 19. Cover Photo Rules

A memory may define one cover photo.

Rules:

- The selected cover must belong to the memory.
- If the selected cover is deleted, use the first remaining photo.
- If no photos remain, set the cover ID to `null`.
- If no cover is explicitly selected, use the first photo by gallery order.
- Editing text must not disturb cover selection.
- Reordering photos must not invalidate the selected cover.

## 32. Rendering Strategy

The Adventure Book should render from the active Adventure Record and stored media.

A typical render cycle:

1. Load the active Adventure.
2. List memories through the Memory Journal.
3. Load related media metadata.
4. Build memory view models.
5. Apply search.
6. Apply filters.
7. Apply sorting.
8. Group by Adventure day.
9. Render navigation and memory cards.
10. Restore relevant focus after user actions.

After a successful create, update, favorite toggle, media change, or delete:

- Refresh the canonical active Adventure.
- Rebuild the timeline.
- Re-render only as broadly as necessary.
- Preserve the user’s current day or filter where practical.

## 33. Error Handling

The UI should provide calm, actionable feedback.

Required cases include:

- No active Adventure.
- Memory save failure.
- Media storage unavailable.
- Photo save failure.
- Unsupported file type.
- Missing media record.
- Corrupted memory data.
- Missing linked adventurer.
- Missing linked activity or reservation.
- Delete failure.
- Search or filter producing no matches.

Failure in one photo should not necessarily discard the entire memory when a safe partial-save strategy is possible.

The implementation must avoid silently losing user-written text.

## 35. Performance

Expected Smokies usage is modest, but the architecture should avoid obvious scaling problems.

Requirements:

- Do not embed base64 photo data in the Adventure Record.
- Load media through the media store.
- Avoid repeated full-database scans during one render where possible.
- Avoid recreating object URLs without revoking them.
- Avoid loading full-resolution images when thumbnails are sufficient.
- Keep search and filtering in-memory for the active Adventure.
- Preserve responsiveness on mid-range mobile devices.

Thumbnail generation may be considered if full-size photo rendering becomes too expensive.
